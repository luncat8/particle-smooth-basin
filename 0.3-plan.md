# 0.3 measured frame-time and thermal tuning

## goal

Keep the v0.2 model, `file://` operation, and classic-script/no-build architecture while making representative scenes fit a 60 Hz browser frame. Optimize the stage that is actually slow. A WebGPU backend is a conditional later stage, not the starting assumption.

## baseline and decision

The DOM-free CPU engine measures about 0.6 ms/frame at 810 beads and 1.3 ms/frame at the 1500-bead cap on the reference Node runtime at 1280×800. That is under 10% of a 60 Hz frame before rendering. Porting physics alone cannot establish a browser speedup, and Canvas2D sprite draws, device pixel ratio, gradients, paths, and links are still unmeasured.

First measure complete frames in the target browser. Preserve the seeded Node physics baseline as a regression reference. Only consider WebGPU if representative frame time misses budget and the profile shows GPU-parallel simulation or rendering would remove that bottleneck.

## architecture

- Keep the CPU engine as the correctness reference and primary backend. Controls, interactions, thermal model, and visual semantics stay unchanged.
- Add an optional local profile mode selected by `?profile=1` (works with `file://`). Using `performance.now()`, record stage timings for `stepWorld`, `render`, and the whole callback. After 300 frames, show or log median and p95 frame, simulation, and render times. All sample storage is preallocated; profiling must not add per-frame strings or arrays. The recorder is `js/profile.js` and is shared with the matrix harness so page and harness numbers mean the same thing.
- Run the matrix — DPR 1 and 2, temperature view on/off, one cold/high-link preset, and 300, 810, and 1500 beads — from `tests.html`, which `run_tests.py` serves and opens. Every case reports p50/p95 for the callback, `stepWorld`, `render`, and the `requestAnimationFrame` interval; the interval is what exposes compositor or raster cost that callback timing hides. Re-run after each rendering change against the same seeded bed.
- Keep hot-path work allocation-free: cache grid cells and pair radius sums, cache static tank `Path2D` outlines and gradients at resize, use pre-rendered sprites, and draw only mechanically effective thermal links.
- If p95 remains above 16.7 ms, reduce visual work in this order: link pass count, redundant water-surface passes, then render DPR by a pixel budget. Never lengthen the fixed 120 Hz physics substep to hide a rendering problem.
- Tune cold/hot source placement and rate while watching link count and mean temperature; cold links and thawing must be visible at the default rates, without requiring extreme splashes.
- The zone bands live on the world as `coldZoneEnd` / `hotZoneStart` (share of H) and the drawn gradients read the same numbers, so what is measured is what is shown. `experiments/thermal-zone.js` sweeps the pair and the source rate against a seeded bed and reports active links, bondable bead count, band temperatures, link churn and stir recovery.
- Measured decision: the shipped cold band ends at `0.40` instead of `0.24`. At `0.24` only ~23 of 810 beads got cold enough to bond (60 links) after 8 s at 1x — the band ended above the settled bed. At `0.40` the bed's upper half is cold (top band 0.25, bottom band 0.83) and carries ~500 links, the bottom stays fluid, a splash thaws and re-forms them, and the frame cost is unchanged (0.85 vs 0.92 ms/frame seeded). `0.44` doubles the cold-bond count again and is the next step if this still reads too subtle in the browser.

## WebGPU gate

Result of the first real-device capture (`experiments/logs/0.3.1-tests-2026-10-25-23-47-16.log`, Windows, Chrome 151, DPR 1.25, NVIDIA): worst frame p95 is 2.22 ms at the 1500-bead stirred cap, and every case's frame p95 sits under 2.3 ms while the rAF interval stays pinned at the 5.6 ms display refresh. The CPU/Canvas2D path is not the bottleneck, so the first gate condition fails: do not start a port. Keep the measurements as the regression reference.

The gate is met only when all of these hold:

- Browser p95 frame time exceeds 16.7 ms on a target device at the default scene, or a useful higher particle count is blocked.
- The profile attributes a substantial share to simulation, broadphase, or bead draws that can be moved to GPU without per-frame CPU readback.
- Target browsers permit WebGPU for the local page, or a documented local-serving workflow is accepted before implementation.

If the gate passes, add a local classic-script backend with structure-of-arrays buffers for positions/velocities, radius/density, temperature, and bonds. Separate compute passes for thermal exchange/sizing, integration, broadphase/contact/bond constraints, and instanced rendering. Match CPU unordered-pair semantics and do not silently drop pairs. Upload compact parameter changes; read back only sampled statistics and interaction results. Keep the CPU engine as fallback, and on device loss show a concise status and restart the CPU bed with current controls.

## validation

- `node experiments/bench.js` with the seeded bed: no NaN at defaults, after splash, and at extreme size/buoyancy combinations; record throughput and peak effective/cold link counts.
- `node experiments/thermal.js`: independent source/conduction rates, normalized temperature, size response, buoyancy bounds, persistent rest lengths, warm thawing, no long-range links, pointer gating, and frame-rate-independent wave state.
- `node experiments/smoke.js`: classic-script boot/render, all presets, live controls, re-deal, DPR change, and pointer cancel.
- Browser harness (`run_tests.py` → `tests.html`): checks that the page boots the shipped scripts, that beads repaint the canvas, that link/pair invariants and temperature bounds hold under splash and drag, that resize and DPR changes re-deal cleanly, that the default rates leave the bed visibly bonded (cold beads ≥ 100 and ≥ 200 active bonds after 4 s at 1x, top band colder than bottom, and no bonds with the source off), and that the profiler reports once and stops. Perf matrix: 300/810/1500 beads, DPR 1/2, temperature view on/off, cold/high-link preset, stirred near-cap scene. The page appends its section to the same timestamped log as the node checks, so one capture holds both halves; the server is cross-origin isolated so timers are not coarsened. Verify no per-frame allocation growth over 600 frames.
- Invariants: `linkActiveN <= linkN <= pairN <= pair-buffer capacity`, no stale warm or separated constraints, no NaN/Inf, hover does not stir, held pointer does, and fixed-step wave state matches at 60 Hz and 120 Hz frame rates.

## go/no-go

Ship CPU/Canvas2D optimizations when default and near-cap scenes stay within budget and no visual regression is visible. Proceed to WebGPU only when the gate is met and a prototype beats the measured end-to-end frame time, including upload/readback overhead, on more than one target device.

## next step

The frame budget is met with large margin, so the plan's remaining item is the live-feel work: tune cold/hot source placement and rates so cold links and thawing are visible without extreme splashes. Re-run `python3 run_tests.py` after each tuning change and compare the perf rows and the link counts against `experiments/logs/0.3.1-tests-2026-10-25-23-47-16.log`; a regression would show up first as a higher frame p95 at the 1500-bead cases or a jump in the cold-links active-link count.
