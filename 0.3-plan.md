# 0.3 WebGPU port

## goal

Port the thermal basin's measured GPU-suitable work to WebGPU without changing the v0.2 model or adding a build system or remote dependencies.

## prerequisite

Profile the shipped v0.2 at the target particle counts first. A port is justified only if simulation or rendering is a meaningful frame-time bottleneck; preserve the measured CPU baseline so the GPU port can be compared rather than assumed faster.

## architecture

- Keep the current DOM-free CPU engine as the correctness reference and retain the same controls, interactions, and visual semantics.
- Add a local classic-script WebGPU backend. Keep shader source in local files or embedded strings; do not add external libraries, module loading, or network dependencies.
- Use structure-of-arrays GPU buffers for particle position/velocity, radius/density, temperature, and thermal bonds. Avoid per-frame CPU readback; read back only sampled statistics and interaction results when needed.
- Separate compute passes for thermal exchange/size update, particle integration, broadphase/contact and bond constraints, and rendering. The WebGPU broadphase must match CPU unordered-pair semantics and must not silently drop pairs.
- Keep inputs and controls on the CPU, upload compact parameter changes, and map pointer interactions through canvas coordinates.

## compatibility and failure behavior

- Detect WebGPU availability before requesting an adapter/device. If unsupported or device initialization fails, continue using the CPU engine with the same UI; this is a deliberate backend choice, not a second legacy product.
- Keep `file://` operation and local assets as acceptance requirements. Verify the target browsers permit WebGPU for the local page; if not, document the minimum local serving requirement before implementation rather than silently breaking the current workflow.
- Handle device loss by presenting a concise status and restarting the CPU reference bed with the current controls; do not imply that an unsynchronized GPU state is preserved.

## validation and go/no-go

- Compare trajectories and aggregate temperature, radius, link count, and particle distribution against the CPU reference under seeded initial conditions.
- Confirm no NaN/Inf, no pair-buffer overflow, correct link thawing, and equivalent grab/splash behavior.
- Benchmark 300, 650, and near-cap particle scenes on multiple devices, including transfer/readback overhead.
- Proceed only if the GPU backend improves representative frame time or enables a useful higher particle count without compromising the current baseline.
