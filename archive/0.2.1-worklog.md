# 0.2.1 archimedes-vs-size worklog

## review of 0.2.0

Two real issues in the shipped base:

- `addBead` could roll a radius up to 1.30× the typical radius while `rMax` and the pair grid assumed 1.28×. Two maximal added beads can be more than one grid cell apart and still overlap at `pairRF` distance, slipping past the unordered-pair stencil. Spawns and the grid bound now share one `SIZE_FACTOR_MAX`.
- `updateThermalSize` ran `Math.pow` per bead per substep even at size response 0 (the default). The transcendental is now skipped when the response is zero; the new archimedes factor gets the same shortcut.

Everything else in the 0.2.0 seams (SoA layout, persistent link hash, coverage-based deal, cached sprites, DOM-free engine) held up under review.

## archimedes force vs size

- Model: buoyant acceleration scales by `(r / typicalRadius)^a`, signed `a` in [-1, 1] — the new slider. `a = 0`, the default, keeps buoyancy size-independent, so thermal shrinking stays a pure flow tool and never silently changes floating. Positive `a` makes large beads more buoyant, negative less. Weight, density, and mass stay on their existing models; only the Archimedes term is modulated.
- `js/engine.js` applies the lift factor inside the gravity-vs-Archimedes line; `setArchSize` is live, no re-deal needed.
- `index.html` / `js/app.js` add the slider; `0.2-plan.md` and `README.md` document the term. Supplied drafts stay untouched.

## validation

- `node --check` on all three page scripts — clean.
- `node experiments/thermal.js` — zero response leaves neutral beads hovering at any radius exactly, +1 lifts only the double-radius bead, -1 sinks it; all previous checks pass.
- `node experiments/smoke.js` — slider wired and labeled (`+0.50` at input 0.5).
- `node experiments/bench.js` — 0.53 ms/frame at 810 beads (0.52 in 0.2.0); settle and splash unchanged, no NaN; extreme combo `a=1, thermal size=-0.5` settles at max|v|=3; default `a=0` preserves the Archimedes equilibrium exactly (0.500 / 1.000). Near-cap profile: 1500 beads at 1.19 ms/frame, peak pairs 3751/12000. Numbers in `experiments/logs/0.2.1.txt`.

## next step

The profile settles the 0.3 go/no-go: CPU simulation is ~0.5 ms (810 beads) to ~1.2 ms (the 1500 cap) per frame, under 10% of a 60 Hz budget before rendering — the WebGPU port is not warranted, `0.3-plan.md` stays shelved. Next candidate: a small gui plan with presets for the thermal-size × arch-size sign combos (hot-shrinks-flow, big-floats, convection-style loops) so the new coupling can be felt quickly, then tune source/conduction rates by feel in the preview.
