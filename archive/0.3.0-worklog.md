# 0.3.0 profile stage timer worklog

## review of 0.2.3

- Re-checked the hot-path fixes (pointer `down` gating, cold-bond rebuild/thaw, fixed-step waves, cached `Path2D`/gradients). No regression or leftover issue found; the bench numbers reproduce (810 beads 0.57 ms/frame, 1500 beads 1.39 ms/frame, no NaN, equilibrium 0.500/1.000 unchanged).
- The one open item was the measured end-to-end frame time: Node only proves the simulation stage, so the `0.3-plan.md` WebGPU gate could not be evaluated.

## implementation

- Added the optional `?profile=1` stage timer to `js/app.js`. Three preallocated `Float64Array(300)` buffers record whole-callback, `stepWorld`, and `render` durations via `performance.now()`; after 300 frames the stats line and console show p50/p95 for frame, simulation, and render. Typed-array `slice().sort()` gives numeric percentiles with a single one-off allocation at report time.
- Profiling is completely off without the query flag: the frame loop takes the original untimed path, and no strings or arrays are built per frame while profiling.
- A finished profile is not overwritten by the periodic stats refresh (`updateStats` returns once a profile is done), so the result stays readable on screen.
- Mode detection accepts both the browser global `location` and `window.location`, which keeps the DOM-free Node smoke harness able to exercise the exact shipped bundle.
- Extended `experiments/smoke.js`: the fake-DOM sandbox is now a small factory, and a second bundle instance runs with `?profile=1` and a monotonic fake clock. It asserts the profile reports after exactly 300 frames with the deterministic stage split and stays on screen for later frames.
- Documented the profile mode in `README.md` and updated the `0.3-plan.md` next step to the browser capture matrix.
